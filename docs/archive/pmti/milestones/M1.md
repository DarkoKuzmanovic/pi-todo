## Goal

`pi-todo` reconstructs canonical todo store state, `TaskTracker` state, and the compact above-editor widget correctly after `/compact` or auto-compaction, with explicit extension-owned persistence rather than relying only on old todo tool results remaining in the append-only session branch.

## User-visible / operational value

After M1, long Pi sessions can compact safely without losing task context, prompt injection state, command-helper task lookup, or compact widget progress. This protects the main reason `pi-todo` exists: keeping the agent and user aligned when context pressure grows.

## Scope

### In

- Lock the Pi `session_before_compact` / `session_compact` event contract needed for extension-owned task persistence.
- Persist a durable, JSON-serializable `pi-todo` compaction snapshot via `pi.appendEntry()` / `CustomEntry`, not by replacing Pi's default `CompactionResult` or writing into `CompactionEntry.details`.
- Acknowledge current behavior: `getBranch()` already returns all branch entries, including older todo tool results after compaction, so M1 turns accidental correctness into intentional resilience.
- Make canonical store reconstruction and runtime tracker reconstruction use the same replay source and malformed-data rules.
- Register compaction lifecycle handling so `session_before_compact` persists the snapshot, `session_compact` refreshes widgets, and celebrations are not replayed spuriously.
- Add focused Vitest coverage for compacted branches, appended custom snapshots, malformed replay details, tracker/store symmetry, and widget refresh behavior.
- Verify `/compact` or an equivalent manual trial after tests pass.
- Record DeepSeek v4 Pro trial evidence from M1-T2: wall-clock, API usage/cost if available, verification results, reviewer/fix-back burden, scope discipline, and notable failure modes.

### Out

- Public tool schema changes for `todo_write`, `todo_read`, or `todo_remove`.
- Dependency metadata, tombstones, or rich optional task fields.
- Permanent deletion or archiving of `../oh-my-todo/`.
- Replacing `/tree` branch-summary behavior beyond preserving existing `session_tree` reconstruction.
- Broad refactors of UI rendering unrelated to replay/compaction.

## Acceptance criteria

- A branch containing an appended `pi-todo` `CustomEntry` snapshot but no usable earlier todo tool results reconstructs the same task list into both `store` and `runtime.tracker`.
- If later `todo_write` / `todo_remove` results exist after a compaction snapshot, the later tool result wins.
- Malformed or missing compaction snapshot data cannot leave store and tracker divergent; both projections clear or recover according to the same rule.
- `session_compact` refreshes both the legacy `pi-todo` status/footer state and the `pi-todo-compact` above-editor widget when UI is available.
- Reconstructing after compaction does not emit task-completion celebrations for already-completed tasks.
- Existing `/todos`, `/done`, `/start`, `/next`, `/pause`, and before-agent prompt injection see the reconstructed state after compaction.
- Focused tests and full `npm test` pass.
- Extension lint/format check has no new parse or lint errors beyond documented pre-existing warnings.
- Manual `/compact` or equivalent reload/trial verification is recorded before closing M1.

## Constraints / invariants

- **Single replay invariant:** canonical `store` and runtime `TaskTracker` must be reconstructed from the same effective task-details source.
- **Latest valid state wins:** later todo tool results after a compaction snapshot override the snapshot.
- **Malformed latest replay input is symmetric:** invalid latest replay data must not let one projection preserve old tasks while the other clears or diverges.
- **No celebration replay:** lifecycle reconstruction must refresh UI but not notify completion milestones.
- **No public schema churn:** compaction snapshots are internal extension state, not changes to `todo_write` / `todo_read` / `todo_remove` inputs or outputs.
- **DeepSeek trial discipline:** at least one M1 task packet should route to DeepSeek v4 Pro and record comparable evidence; GLM 5.1 should not be used unless the user explicitly re-approves it.
- **Compaction lifecycle reality:** `session_start` does not fire after `/compact`; `session_before_compact` is the pre-compaction persistence point and `session_compact` is the post-compaction refresh point.
- **Append-only branch reality:** `getBranch()` currently includes old tool results even after compaction; M1 should preserve that behavior in tests while adding explicit snapshot resilience.
- **AGENTS.md replay lesson:** malformed or missing latest replay details must clear every projection the same way.

## Oracle review

Status: completed 2026-06-01 — approve with amendments; blocker amendment applied in this milestone file before task-packet preparation.

Oracle findings accepted into this plan:

- **B1:** Do not store task snapshots in `CompactionEntry.details`; `SessionBeforeCompactResult.compaction` replaces the whole default compaction. Use `pi.appendEntry()` / `CustomEntry` for non-disruptive persistence.
- **I1:** `session_start` does not fire after compaction; `session_compact` is the post-compaction event.
- **I2:** `getBranch()` already returns old tool results after compaction, so M1 hardens accidental correctness into explicit resilience.
- **I3:** Move the DeepSeek v4 Pro trial from architecture-heavy M1-T1 to the more mechanical M1-T2 reconstruction refactor.
- **I4:** Clarify hook ownership: `session_before_compact` persists snapshots, `session_compact` refreshes widgets/state.

Source evidence checked locally: Pi extension types expose `SessionBeforeCompactResult` with only `cancel?: boolean` and `compaction?: CompactionResult`, and `pi.appendEntry(customType, data)` for custom persistence; `getBranch()` docs say it returns all entry types in path order.
