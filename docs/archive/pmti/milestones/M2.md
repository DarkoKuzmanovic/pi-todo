## Goal

Add optional `blockedBy` dependency metadata to `pi-todo` so tasks can explicitly depend on other tasks, invalid dependency graphs are rejected or normalized safely, and blocked work is visible in prompt/UI surfaces without changing the existing public tool names or making dependency metadata mandatory.

## User-visible / operational value

Agents can encode task ordering constraints directly in the task list instead of relying only on prose ordering. This should make `/next`, prompt injection, `/todos`, and compact status less likely to suggest blocked work while preserving the simple task model for sessions that do not need dependencies.

## Scope

### In

- Extend the internal/public task shape with optional `blockedBy?: string[]` dependency IDs while keeping existing valid tasks valid.
- Update TypeBox tool schemas and TypeScript task types for optional dependency metadata.
- Extract `blockedBy` faithfully through session replay, compaction snapshots, store, tracker, and tool-result details; validate/normalize dependency graphs only at the `todo_write` input boundary.
- Validate dependency references enough to prevent self-dependencies, duplicate dependency IDs, unknown dependency IDs, and dependency cycles from silently entering canonical state.
- Define blocked semantics: a task is blocked when it is not completed and at least one dependency ID points to a non-completed task.
- Update prompt/list/widget surfaces enough that blocked state is visible and blocked pending work is not promoted ahead of unblocked work.
- Add focused Vitest coverage for valid dependencies, invalid references, cycles, reconstruction, `/next`, prompt injection, `/todos`, and compact blocked-state display.
- Keep helper commands auditable: commands should still send follow-up instructions rather than mutating tasks directly.

### Out

- Do not replace `todo_write`, `todo_read`, or `todo_remove` with a single generic tool.
- Do not make `blockedBy` mandatory.
- Do not implement tombstones/deleted-task history (M3), rich fields such as `description`/`owner`/`metadata`/`activeForm` (M4), or `oh-my-todo` archival/deletion (M5).
- Do not introduce network dependencies, telemetry, persistent files outside Pi session/custom entries, or a database.
- Do not silently mutate task status behind the model just because a dependency becomes unblocked.
- Do not change unrelated compact-widget styling except what is needed to represent blocked state.

## Acceptance criteria

- Existing task payloads without `blockedBy` remain valid and behave as they did before M2.
- Valid `blockedBy` arrays survive `todo_write`, `todo_read`, `todo_remove`, replay reconstruction, and `pi-todo:snapshot` compaction persistence.
- Invalid dependency graphs follow the oracle policy: strip self-dependencies and duplicate dependency IDs silently, strip unknown dependency IDs with a warning in tool result text, allow dependencies on completed tasks, and reject cycles atomically without changing canonical state.
- Store and runtime tracker agree on blocked/unblocked status after normal tool results and after compaction replay.
- `before_agent_start` prompt injection indicates blocked tasks and does not tell the agent to start blocked pending work ahead of unblocked pending work.
- `/next` selects only unblocked pending tasks when possible and reports clearly when all remaining pending tasks are blocked.
- `/todos` and compact widget/status surfaces show blocked state concisely without overwhelming the UI.
- Focused M2 tests, full `npm test`, and extension Biome check pass with no new parse/lint errors beyond documented pre-existing warnings.
- Final orchestrator review after M2-T4 has no Critical or Important blockers before M2 close-out.
- Manual or equivalent live trial verifies a small dependency graph through `todo_write`, prompt/widget visibility, `/next`, `/todos`, and unblock behavior after completing dependencies.

## Phase boundary health

M2 is coherent as a standalone milestone because dependency metadata strengthens the existing task model without requiring tombstones or rich task fields. After M2, projects that never use `blockedBy` should experience the same behavior as M1, while projects that do use it gain safer ordering constraints. Later M3/M4 work can build on this metadata without reworking replay or compaction.

## Constraints / invariants

- **Backward compatibility:** old task details without `blockedBy` remain valid and reconstruct exactly as unblocked tasks.
- **Single replay invariant:** `blockedBy` extraction must flow through the same shared extraction/replay boundary used by store and tracker; dependency normalization/validation happens only at the `todo_write` input boundary.
- **No silent graph corruption:** invalid dependency references or cycles must not produce divergent store/tracker state or quietly alter unrelated tasks.
- **Blocked is derived state:** do not store a separate persistent `blocked` status; derive it from `blockedBy` plus current completion state.
- **Completed dependencies unblock dependents:** a dependency only blocks while the referenced task is not completed.
- **No hidden mutation:** helper commands and display logic may recommend actions, but actual state changes still go through `todo_write`.
- **Prompt budget discipline:** blocked-state text should be concise; do not dump full dependency graphs into every prompt turn.
- **Experimental cadence:** MiniMax M3 owns implementation across M2-T1 through M2-T4, but architecture decisions and final acceptance remain with the orchestrator; if MiniMax hits ambiguity, a mandatory stop condition, or failing verification it must stop and report rather than decide a policy silently.
