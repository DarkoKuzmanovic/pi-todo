## Goal

Make `todo_remove` audit-friendly by converting task removal into a soft-delete (tombstone) that preserves removed tasks in history and replay while hiding them from every normal read/derived surface (prompt injection, `/todos`, `todo_read`, compact widget). Existing task payloads and the public tool names stay unchanged; tombstoning is additive and backward compatible.

## User-visible / operational value

Agents and humans get a recoverable audit trail of what was removed and when, without cluttering the active task list or prompt budget. Normal task workflows behave exactly as before (removed tasks vanish from view), but the underlying history is preserved through compaction/replay so a future toggle (parked) or audit could surface it.

## Scope

### In

- Add an optional additive tombstone marker to the task shape: `deletedAt?: number` (epoch milliseconds). Presence means tombstoned; absence means a live task. Existing tasks without it remain valid and live.
- Add the optional `deletedAt?: number` field to the stored `Task` type and `TaskDetails` only (audit timestamp; omission means not deleted) — NOT to the `todo_write` input schema `TaskSchema`/`TodoWriteParams`, so tombstoning stays an explicit `todo_remove` action (oracle I3).
- Change `todo_remove` execute behavior to soft-delete: stamp `deletedAt` on the targeted task(s) and persist them in the tool-result details instead of erasing them from canonical state.
- Hide tombstoned tasks from every normal surface: `todo_read`, `formatListForLLM()`, `buildSystemPromptBlock()` prompt injection, `/todos` (both the LLM-text path and the interactive `TodoViewComponent` UI), and the compact widget counts/markers.
- Preserve tombstones faithfully through session replay, `pi-todo:snapshot` compaction persistence, store, and tracker reconstruction. `extractTasks()` must extract `deletedAt` without re-deriving or stripping it.
- Define and implement tombstone interaction with M2 dependency metadata: a `blockedBy` reference to a tombstoned task must NOT block its dependents (tombstoned deps are treated as gone/resolved), and `isBlocked` must ignore tombstoned tasks. Tombstoned tasks are themselves never reported as blocked/active.
- Ensure `todo_write` does not resurrect or duplicate tombstoned tasks unexpectedly; define what happens if a `todo_write` re-sends an ID that is currently tombstoned (oracle-reviewed; default: an explicit `todo_write` with that ID produces a live task again, since `todo_write` is the canonical authoring path).
- Add focused Vitest coverage for soft-delete behavior, hiding across all surfaces, blockedBy-vs-tombstone interaction, reconstruction symmetry, and end-to-end replay survival.

### Out

- No hard purge / permanent deletion path in M3 (kept in the parking lot until the tombstone model proves stable).
- No `/todos` reveal toggle for tombstoned tasks (explicitly parked; M3 keeps tombstones fully hidden).
- Do not replace `todo_write`, `todo_read`, or `todo_remove` with a single generic tool.
- Do not implement M4 rich fields (`description`, `owner`, `metadata`, `activeForm`) or M5 `oh-my-todo` archival/deletion.
- Do not introduce network dependencies, telemetry, persistent files outside Pi session/custom entries, or a database.
- Do not change unrelated compact-widget styling except what is needed to exclude tombstones.

## Acceptance criteria

- Existing task payloads without `deletedAt` remain valid and behave exactly as before M3 (live tasks).
- `todo_remove` no longer erases targeted tasks from canonical history: the task is stamped with `deletedAt` and retained, but disappears from `todo_read` and all derived/UI surfaces.
- **(B1)** A tombstone survives a subsequent `todo_write` that omits the removed id: `todo_write` preserves non-resent tombstones (merging them after validation) into both canonical state and result `details`, so the audit trail is not erased by the agent's full-list replace.
- Tombstoned tasks are excluded from prompt injection, `formatListForLLM()`, `/todos` LLM-text output, the interactive `/todos` UI, and compact widget counts/markers.
- A `blockedBy` reference to a tombstoned task does not block dependents; `isBlocked` ignores tombstoned tasks; tombstoned tasks are never themselves shown as blocked or active.
- Tombstones survive `todo_write`/`todo_remove` results, replay reconstruction, and `pi-todo:snapshot` compaction persistence; store and runtime tracker agree on which tasks are tombstoned after normal results and after compaction replay.
- `extractTasks()` extracts `deletedAt` faithfully without re-deriving or stripping it (replay is not a tombstoning boundary).
- Re-sending a tombstoned ID via `todo_write` behaves per the oracle-confirmed policy (default: it becomes a live task again) and is covered by a test.
- Focused M3 tests, full `npm test`, and the extension Biome check pass with no new parse/lint errors beyond the documented pre-existing `src/state.test.ts` unused `before` warning.
- Final per-task reviews find no Critical or Important blockers before M3 close-out.
- Manual or equivalent live trial verifies removing a task hides it everywhere, history/replay still contains it, and a `/compact` reconstructs the tombstone correctly.

## Phase boundary health

M3 is coherent as a standalone milestone because soft-delete strengthens the audit story without requiring rich task fields (M4) or `oh-my-todo` retirement (M5). After M3, projects that never remove tasks behave identically to M2; projects that use `todo_remove` gain recoverable history with no visible clutter. The additive `deletedAt` field and the replay-faithful extraction leave later milestones free to add a reveal toggle or hard-purge without reworking persistence.

## Constraints / invariants

- **Backward compatibility:** old task details without `deletedAt` remain valid and reconstruct exactly as live tasks.
- **Additive schema evolution:** `deletedAt?: number` is optional; omission means not deleted. Public tool names are unchanged.
- **Single replay invariant:** `deletedAt` extraction flows through the same shared extraction/replay boundary used by store and tracker; tombstoning happens only at the `todo_remove` input boundary, never at replay/extraction time.
- **No silent mutation:** removal still goes through an explicit `todo_remove` call; helper commands continue to recommend actions and route mutations through the public tools.
- **Tombstone is hidden, not derived-away:** tombstones are persisted state (a stored `deletedAt`), but every read/derived/UI surface filters them out. Do not store a parallel "deleted list" that can diverge from the canonical tasks.
- **No graph corruption with M2:** tombstoned tasks must not produce divergent store/tracker state and must not block dependents through stale `blockedBy` references.
- **Prompt budget discipline:** hiding tombstones must not add per-turn prompt text; the prompt should simply omit them.
- **DeepSeek trial discipline:** record model handle, wall-clock, API usage/cost if visible, verification, reviewer/fix-back burden, scope discipline, code quality, and notable failure modes (compare against M0 MiniMax/GLM and M1 DeepSeek/Sonnet evidence).

Scope (T1 is the invariant-defining task; it is materially larger than "stamp + retain" because `todo_write` preservation is the real linchpin — oracle B1):
- **Schema placement (I3):** add `deletedAt?: number` to the stored `Task` type (`src/types.ts`) and to `TaskDetails` ONLY. Do NOT add it to `TodoWriteParams`/`TaskSchema` (`src/schemas.ts`), so the model cannot author born-tombstoned tasks or tombstone via write; tombstoning stays an explicit-`todo_remove` action.
- **`todo_remove` soft-delete (M-c):** replace `removeByIds` (`src/state.ts:34`) erase semantics with stamping `deletedAt = Date.now()` on targeted live tasks and retaining them in canonical state + tool-result details. Stamping is idempotent: re-removing an already-tombstoned id is a no-op and is NOT counted in the "removed N" message; the message reflects only newly-tombstoned live ids.
- **`todo_write` tombstone preservation (BLOCKER B1):** `todo_write` does a full-replace (`store.setTasks`) from the agent's COMPLETE list, but the agent cannot see hidden tombstones and will omit them — which would erase them on the next write. After validation succeeds, compute stored tombstoned tasks whose ids are NOT in the incoming candidate id set and persist `store.setTasks([...validatedCandidates, ...preservedTombstones])`, with preserved tombstones also flowing into result `details.tasks`.
- **Validation ordering + re-send (I2, re-send policy):** run M2 `validateDependencyGraph` over the LIVE candidates only, THEN merge preserved tombstones. A re-sent tombstoned id (present in candidates) resurrects to live and MUST clear `deletedAt` (candidate-building does not copy it — assert it). A live task's `blockedBy` pointing at a tombstoned, not-resent id is absent from candidates and is therefore stripped-with-warning by existing `normalizeBlockedBy` (desired: "cannot depend on a deleted task"); no new normalization code.
- **Replay faithfulness (I3 symmetry trap):** `extractTasks()` in `src/tracker.ts` whitelists fields, so it MUST extract `deletedAt` with safe coercion consistent with siblings (`deletedAt: t.deletedAt != null ? Number(t.deletedAt) : undefined`). Omitting it there would silently drop tombstones on every replay/compaction and resurrect deleted tasks.
- **`isBlocked` safety net (I2):** `isBlocked` (`src/deps.ts`) ignores tombstoned tasks as defense-in-depth for reconstructed display state (older replayed details may still carry a `blockedBy` to a tombstoned id). This cannot hide a real ordering constraint because a tombstoned dependency is removed/non-actionable.
- **Pure helpers:** add small dependency-agnostic helpers (`isTombstoned(task)`, an `activeTasks(tasks)` live filter) in `src/deps.ts` or a new `src/tombstone.ts`.
- **Description/doc accuracy (I4):** update the soft-delete-inaccurate strings that ship with this behavior change — `todo_remove` tool description and `index.ts` file header ("permanent/permanently delete"), the prompt guidelines, and `TodoRemoveParams` description (`src/schemas.ts`, "remove from the list permanently"). README/CHANGELOG are deferred to M3-T4.

Acceptance:
- Existing tests stay green for tasks without `deletedAt`.
- **B1 test:** `todo_write` after a `todo_remove`, omitting the removed id, retains the tombstone in canonical state AND in result `details`.
- **Round-trip test (I3):** a tombstone survives a round-trip through `extractTasks()`/snapshot (hard T1 acceptance).
- **Resurrection test:** re-sending a tombstoned id via `todo_write` produces a live task with `deletedAt` cleared.
- **Strip-with-warning test (I2):** a live task depending on a tombstoned, not-resent id is stripped with the unknown-id warning.
- Idempotent-remove test: re-removing a tombstoned id is a no-op and not counted in "removed N".
- Store/tracker reconstruction stays symmetric for the tombstone marker.

### Blocker (resolved in this plan)

- **B1 — `todo_write` full-replace erases hidden tombstones.** `todo_write` replaces the whole list from the agent's COMPLETE payload, but the agent cannot see hidden tombstones and will omit them, so the next write would wipe them from canonical state and the latest replay source — collapsing the audit premise after exactly one write. Resolution folded into M3-T1: after validation, preserve stored tombstones whose ids are not in the candidate set via `setTasks([...validatedCandidates, ...preservedTombstones])` and carry them into `details`; tested with a remove→write retention test.

### Confirmed (no change)

- `deletedAt?: number` representation — better than a boolean (carries the audit timestamp) and far safer than a `status: "deleted"` enum (huge blast radius through `validStatus`, transitions, diffs, widgets). Keeping tombstones in the canonical list also preserves `syncIdCounter`'s max-id scan, preventing id reuse.
- Re-send policy = resurrect-to-live, falling out of the merge-after-validation design; resurrection must clear `deletedAt` (asserted).
- Soft-delete only, no hard purge — phase boundary stays coherent; only the agent's full-replace mental model relied on hard deletion, which B1 addresses.
- Task graph T1 → {T2, T3} → T4 with rebalanced scope (T1 = invariant-defining incl. todo_write preservation; T2 = tracker/runtime/command/widget filtering; T3 = persistence symmetry).
- Per-task review cadence — correct for this replay/persistence-invariant-sensitive work.
