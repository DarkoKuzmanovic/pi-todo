# M11 — Delta ops: `todo_patch`

*Spec date: 2026-08-14. Status: proposed (not yet an active build; graduates to `PLAN.md` when started).*

## 1. Context and motivation

`todo_write` is a full-list replace: checkmarking task 12 of 15 re-emits all 15
tasks. Cost is O(list size) output tokens per update, and long rewrites are
where models occasionally drop or reword unrelated tasks.

Evidence from the 2026-08-13 ecosystem sweep:

- Claude Code itself retired `TodoWrite` in favor of delta-based
  `TaskCreate`/`TaskUpdate`/`TaskList`.
- Every other Pi todo extension surveyed (`@tintinweb/pi-tasks`,
  `@juicesharp/rpiv-todo`, `@jerryan/pi-todo-lite`, `kirang89/pi-todo`,
  `@diegopetrucci/pi-todo`) uses delta updates.
- `pi-todo-lite`'s archive notes name the failure mode deltas mitigate:
  agents batch-create then batch-complete at the end because per-update cost
  discourages granular checkmarking.

M11 adds **one** new tool, `todo_patch`, for cheap targeted mutation of
existing tasks. `todo_write` remains the planning tool and the only way to
create tasks. Contract in one line: **plan with `todo_write`, progress with
`todo_patch`, remove with `todo_remove`.**

## 2. Tool surface

```
todo_patch — Update existing tasks by ID without resending the list.
```

### Parameters (`TodoPatchParams` in `src/schemas.ts`)

```ts
{
  patches: Array<{
    id: string;                 // required; must be a live (non-tombstoned) task
    status?: TaskStatus;
    priority?: TaskPriority;
    content?: string;           // rename
    blockedBy?: string[];       // REPLACES the task's whole blockedBy array; [] clears
    description?: string;       // replaces; "" clears
    appendDescription?: string; // appends "\n\n" + text; excl. with description
    owner?: string;             // replaces; "" clears
    activeForm?: string;        // replaces; "" clears
    metadata?: Record<string, string|number|boolean|null>;
                                // per-key MERGE; null value DELETES that key
  }>  // minItems: 1
}
```

Absent field = unchanged. No task creation, no deletion, no reordering.

### Field semantics

| Field | Merge rule | Clearing |
|---|---|---|
| `status`, `priority` | replace | n/a |
| `content` | replace | not clearable (content is required on Task) |
| `blockedBy` | whole-array replace, then full M2 pipeline reruns on the merged list | `[]` deletes the field |
| `description`, `owner`, `activeForm` | replace | `""` deletes the field |
| `appendDescription` | `stored ? stored + "\n\n" + text : text` | n/a |
| `metadata` | per-key shallow merge | `null` value deletes that key (patch-boundary only; `null` is never stored, I1 preserved) |

`metadata` note: the *patch* schema admits `null` values as delete markers.
Deletions are split out **before** `validateMetadata` runs on the remainder,
so the stored bag stays I1-clean (flat `string|number|boolean`, no nulls).

## 3. Atomicity and error policy

The whole `patches` array is **atomic** — all patches apply or none do.
Consistent with the M2 cycle policy: reject outright when the model's mental
state has demonstrably drifted, warn-and-continue for recoverable noise.

Whole-call rejections (first error wins, canonical state untouched):

1. **Unknown or tombstoned `id`** — a patch for a task that doesn't exist in
   the live list. Error text MUST include `formatListForLLM()` so the model
   resyncs from the authoritative list (self-healing reject).
2. **Duplicate `id` within one call** — ambiguous ordering; reject.
3. **`description` + `appendDescription` on the same patch** — ambiguous.
4. **Malformed `metadata` container** (string/array/non-object) — mirrors the
   `todo_write` I1 preflight.
5. **Dependency cycle** after `blockedBy` merge — same atomic reject and same
   error text shape as `todo_write` (`Dependency cycle detected: …`).

Warn-and-continue (matches `todo_write` exactly, reuses existing formatters):

- Unknown IDs inside a patched `blockedBy` → stripped with
  `formatStrippedWarning`.
- Self-deps / duplicate deps → stripped silently (`dedupeBlockedBy`).
- Invalid metadata keys inside a valid container → per-key drop with named
  warning (I1).

## 4. Implementation: desugar into the `todo_write` pipeline

The core design decision: **`todo_patch` builds a merged candidate list and
runs the exact same tail as `todo_write`.** No second state-mutation path.

```
execute(patches):
  1. live = store.tasks.filter(t => t.deletedAt == null)
  2. Reject-checks 1–4 from §3 against `live` and the patch payloads.
  3. merged = live.map(t => patchesById.has(t.id) ? applyPatch(t, patch) : t)
     — applyPatch is a pure function in a new src/patch.ts; rich-field
       patches route through the existing validateMetadata / typeof-string
       discipline from src/rich-fields.ts.
  4. validation = validateDependencyGraph(merged)      // M2, unchanged
     if (!validation.ok) → atomic reject (§3.5)
  5. B1 tombstone preservation, applyStatusTransitions, setTasks,
     syncIdCounter, runtime.processToolResult("todo_patch", details, ctx)
     — verbatim the todo_write tail (extract it into a shared helper,
       e.g. commitTaskList(candidates, ctx), called by both tools).
```

What this buys for free, because the tail is shared:

- **Timestamps** — `applyStatusTransitions` sees prev-vs-next per task, so
  `startedAt`/`completedAt`/revert-clears behave identically to a
  `todo_write` transition. No new timestamp code.
- **B1** — hidden tombstones outside the candidate set survive, unchanged.
- **No ID minting** — patches never call `generateId()`; `idCounter` is
  untouched and needs no rollback on rejection.
- **Widget/tracker/celebration flow** — `runtime.processToolResult` is the
  same choke point.

## 5. Replay integration (the critical edit)

`src/replay.ts` treats a fixed tool-name set as replay sources. `todo_patch`
results carry the full authoritative list in `details` (same
`TaskDetails = { tasks: [...] }` shape), so it MUST join that set:

- Add `export const TODO_PATCH = "todo_patch"`.
- Widen `TodoToolName` and `isTodoToolName` to include it.

Without this, a `todo_patch` as the latest mutation would be invisible to
`reconstructState` — `/tree` navigation, forks, and post-compaction replay
would resurrect the pre-patch list. This is the one place a missed edit
corrupts state silently; the symmetry test suite (§9) must pin it.

`TODO_SNAPSHOT_VERSION` stays 1 — the snapshot payload shape is unchanged.

## 6. Result payload: terse content, full details

Pi sends only `content` to the model; `details` stays host-side for
rendering and replay. Exploit the split — this is where the real token win
lives (small call args AND small result text):

- **`details`**: full `{ tasks: [...store.tasks] }` snapshot, exactly like
  `todo_write` (replay + renderResult depend on it).
- **`content` on success**: a delta confirmation, NOT `formatListForLLM()`:

  ```
  Patched t3 → completed, t4 → in_progress.
  1 active, 3 pending (1 blocked), 9 done.
  [+ stripped-unknown / metadata warnings when present]
  ```

  Safe because `before_agent_start` re-injects the active list into the
  system prompt every turn — the model is resynced at the next turn boundary
  regardless.
- **`content` on rejection**: the error, then `formatListForLLM()` (§3
  self-healing resync).

## 7. Prompt-guideline changes

Guidelines cost prompt budget in every session; keep the delta tight.

- `todo_patch` gets two bullets:
  - "Use todo_patch to mark a task in_progress or completed, or to adjust one
    task's fields — do not resend the whole list for a status change."
  - "Use appendDescription to add notes to a task without rewriting its
    description."
- `todo_write` guideline edits (replace, don't add):
  - The "Before starting a task, call todo_write to set it to
    'in_progress'" and "Immediately after completing…" bullets change to
    name `todo_patch` as the preferred vehicle for those flips.
  - The REPLACES-the-entire-list bullet gains: "For status flips and
    single-task edits, prefer todo_patch."

Net guideline count stays roughly constant.

## 8. Rendering

- `renderCall`: `todo_patch` + per-patch compact segments, e.g.
  `t3 ✓ completed  t4 ● in_progress` (reuse `STATUS_ICON`, accent/success
  theming to match `todo_write`'s renderCall style; truncate long patch
  lists to a count).
- `renderResult`: `TodoViewComponent.renderTaskResult` on `details` —
  identical to the other two tools.

## 9. Testing obligations

Repo conventions: co-located `.test.ts` per module + symmetry + e2e.

1. **`patch.test.ts`** (new, pure): every merge rule in the §2 table;
   clearing semantics (`""`, `[]`, metadata `null`); appendDescription with
   and without existing description; each §3 rejection.
2. **Equivalence property** (the desugar guarantee): for arbitrary live
   lists and valid patch sets, `todo_patch(patches)` leaves canonical state
   byte-identical to `todo_write(fullMergedList)` — pins against future
   drift between the two paths. A small generator over statuses/fields is
   enough; no fuzzing framework.
3. **`replay` + symmetry**: a branch whose latest mutation is a
   `todo_patch` tool result reconstructs the patched list (store AND
   tracker); post-compaction snapshot ordering unaffected.
4. **Atomicity**: unknown-id rejection leaves state and `idCounter`
   untouched; cycle-via-patch rejection ditto; error content contains the
   full list.
5. **B1/tombstones**: patch call preserves hidden tombstones; patching a
   tombstoned id rejects.
6. **Timestamps**: pending→in_progress sets `startedAt`; →completed sets
   `completedAt`; completed→pending clears it (inherited behavior, but
   asserted through the `todo_patch` entry point).
7. **e2e**: plan via `todo_write`, flip via `todo_patch`, verify widget
   counts, prompt block, `/todos`, and terse content shape.

## 11. Out of scope

- **Widget overflow / collapse** — already planned as **M10** (config file
  with `maxWidgetLines`, `collapseKey`). The pi-tasks survey findings
  (`maxVisible`, completed-drop-first, `hiddenAt`) should be folded into
  M10's scope when it starts, not here.
- **Task creation or deletion via patch** — `todo_write` / `todo_remove`
  own those; keeping patch mutation-only preserves the no-ID-minting
  invariant that makes its rejection path trivial.
- **Stale-task reminders** (pi-todo-lite's `PI_TODO_REMINDER_TOKENS`) —
  explicitly rejected: lite's own archive notes report reminders being
  misread as approval to continue. The per-turn prompt re-injection already
  covers re-anchoring.
- **Partial application / per-patch skip** — atomic-only for V1; revisit
  only if real transcripts show large multi-patch calls failing on one bad
  id.

## 12. Decided defaults (were open questions)

- Batch patches in one call: **yes** (the common "t3 done + t4 started"
  transition is one call).
- `content` renaming via patch: **allowed** — harmless and occasionally
  needed; the equivalence property covers it.
- Result text: **terse delta** (§6), trusting per-turn prompt injection for
  resync.
